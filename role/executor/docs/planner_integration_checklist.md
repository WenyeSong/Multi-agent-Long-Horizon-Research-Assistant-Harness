# Planner Integration Checklist

Use this checklist before connecting `research-planner` to the executor.

The goal is to make the handoff explicit: planner owns task selection and research direction; executor owns bounded execution and artifact production.

## Planner Must Provide

Before invoking executor, planner must provide:

- `request_id`: unique execution request id.
- `planner_id`: parent planner run id.
- `task.title`: short task name.
- `task.objective`: concrete execution objective.
- `task.scope`: allowed algorithmic, experimental, or visualisation scope.
- `workspace.root`: logical execution run root.
- `workspace.read_paths`: explicit read-only input paths.
- `workspace.write_path`: single writable output directory.
- `inputs`: authorised input artifacts with ids, paths, and kinds.
- `success_criteria`: checks executor should validate against.
- `budget.max_attempts`: maximum number of attempts.
- `budget.max_wall_time_minutes`: maximum wall-clock budget.
- `required_outputs`: expected artifact classes.
- `tool_policy_ref`: policy the executor must obey.

## Planner Should Decide

Planner should decide:

- what problem is worth executing;
- what input artifacts are trusted;
- what counts as success;
- when partial results are acceptable;
- whether to call literature reviewer, reviewer, or PDF generator;
- whether executor output should trigger another execution request.

Executor should not make these global decisions.

## Executor Must Return

Executor must return:

- `request_id`;
- `status`;
- concise `summary`;
- artifact references;
- validation result;
- attempt log;
- tool policy observance;
- limitations where relevant.

Executor should return `blocked` or `rejected` instead of guessing when the request is invalid, unsafe, underspecified, or outside policy.

## Workspace Agreement

Planner should create or allocate the run workspace before invocation.

Recommended planner-created layout:

```text
execution_runs/
  <request_id>/
    inputs/
    work/
    figures/
    tables/
    logs/
```

Planner-provided inputs should be copied or linked under `inputs/` where practical. Executor must treat them as read-only.

## Artifact Agreement

Planner should expect:

- core JSON files at the run root;
- figures under `figures/`;
- tables under `tables/`;
- logs under `logs/`;
- scratch code under `work/`;
- all generated artifacts listed in `artifacts.json` and in the executor response.

Planner should not expect large payloads embedded in the executor response.

## Common Integration Failures

Avoid these handoff mistakes:

- Planner gives a vague objective with no success criteria.
- Planner omits `workspace.write_path`.
- Planner provides inputs but does not include them in `workspace.read_paths`.
- Planner expects executor to search the web for missing context.
- Planner expects executor to call reviewer or PDF generator.
- Executor writes outside the assigned run directory.
- Executor returns prose but no machine-readable artifacts.
- Executor reports success without mapping checks to `success_criteria`.

## Minimum Acceptance Before Agent Connection

Before formal agent connection, confirm:

- `schemas/execution_request.schema.json` matches planner's emitted request object.
- `schemas/execution_result.schema.json` matches planner's expected response parser.
- `example_request.json` can be generated by planner with real paths.
- `example_response.json` contains all fields planner needs.
- Tool policy can be enforced by the chosen runtime.
- Workspace paths are either absolute or resolved consistently by both sides.
